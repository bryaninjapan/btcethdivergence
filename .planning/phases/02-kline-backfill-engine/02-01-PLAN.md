# Plan 02-01 — Worker Kline Ingest Engine: Stored Cursor + Chunked D1 Batch Insert

## Objective

Build the Worker-side persistence engine for the locked external-fetcher ingestion path. The Worker no longer talks to Binance (spike proved 403 from Workers IPs); instead it receives already-fetched kline batches over `POST /api/admin/ingest` and persists them with the D1-idiomatic chunked `db.batch()` pattern, while maintaining a per-symbol stored cursor (`backfill_state`) that repeated calls advance forward in time. This is the half of Phase 2 that satisfies the bound-parameter ceiling (SC4) and the stored-cursor advance (SC2) and the "up to 1000 candles stored in D1" persistence half of SC1.

## Success Criteria Coverage

- **SC1** (call the backfill endpoint → a bounded batch of up to 1000 candles stored in D1): Task 2's `POST /api/admin/ingest` accepts and persists up to 1000 klines in one call (verified with a 1000-candle POST). The "fetches from Binance" half of SC1 is plan 02-02 (the external fetcher). Together they satisfy SC1 end-to-end.
- **SC2** (repeated calls advance a stored cursor forward until "now", each call within Free-plan CPU/subrequest limits): Task 1 creates `backfill_state` + `getBackfillCursor`/`setBackfillCursor`; Task 2 advances the cursor on each ingest and Task 2's verify proves two consecutive calls move the cursor forward. The ingest handler performs zero external subrequests and only D1 `batch()` calls, keeping it within the 10ms CPU / 50-subrequest Free limits.
- **SC4** (each batch insert split into chunks of at most 16 rows via `db.batch()`, never exceeding D1's 100 bound-parameter ceiling): Task 1's `buildKlineInsertChunks` + unit test assert every statement is ≤14 rows (≤98 bound params, staying under 100) and that 1000 rows → 72 statements sent as 2 `db.batch()` calls.

## Dependency Graph

- Task 1 (migration + chunk builder + db repository, with unit tests) → Task 2 (ingest + cursor routes, mounted, deployed, curl-verified). Builds on the Phase 1 Worker (`src/routes/admin.ts`, Hono router, D1 binding) from plan 01-02/01-03. Consumed by plan 02-02 (the external fetcher posts into this endpoint).

The klines table has 7 columns (`symbol, open_time, open, high, low, close, volume`), so every row in a multi-row `INSERT` contributes **7 bound params**. To stay under D1's 100-parameter cap, use **rowsPerStmt = 14** (14 rows × 7 params = 98 ≤ 100). This satisfies SC4 verbatim: "chunks of at most 16 rows" (14 ≤ 16) that "never exceed D1's 100 bound-parameter ceiling."
    - `export function chunkKlines<T>(rows: T[], rowsPerStmt = 14): T[][]` — split into arrays of at most `rowsPerStmt` elements.
    - `export function buildKlineInsertChunks(klines: Kline[]): { groups: { sql: string; params: (string | number)[] }[][]; totalStmts: number }`
      - Chunk klines into groups of at most 14 rows.
      - For each group build `INSERT OR IGNORE INTO klines (symbol, open_time, open, high, low, close, volume) VALUES (?, ?, ?, ?, ?, ?, ?),(?),...` — one `(?, ?, ?, ?, ?, ?, ?)` tuple per row; params per statement = `[symbol, r.open_time, r.open, r.high, r.low, r.close, r.volume]` for each row → 7 params/row, 14 rows → 98 params.
      - Group the resulting statements into **`db.batch()` calls of at most 40 statements each** (returned as `groups`, an array of statement arrays). A full 1000-candle batch = 72 statements (ceil(1000/14)) → 2 `db.batch()` calls → 2 D1 round trips, well under the Free 50-subrequest cap (each `db.batch()` is one subrequest).

    Add src/lib/kline-insert.test.ts (vitest):

    - The number of `db.batch()` groups === 2 for 1000 rows (ceil(72/40)).
