# Plan 02-02 — External Fetcher: GitHub Actions Binance Backfill Driver (DATA-01, DATA-05)

## Objective

Build the "fetch from Binance" half of the Phase 2 backfill engine that the spike verdict locked: a cursor-aware fetcher that runs **outside** the Worker (GitHub Actions runner, or the local machine during verification — both reach Binance with HTTP 200, unlike the deployed Worker's 403), pulls at most 1000 candles per run, handles Binance rate limits (`X-MBX-USED-WEIGHT-1M`, `Retry-After` on 429, backoff on 418), and POSTs the parsed klines into the plan 02-01 `/api/admin/ingest` endpoint to be persisted. Each run is one bounded batch; repeated runs (repeated `workflow_dispatch` / local invocations) advance the stored cursor until a short batch signals "reached now" — satisfying SC2's "advance a stored cursor until reaching now" as a callable mechanism.

## Success Criteria Coverage

- **DATA-01** (fetch 1h OHLCV kline data from Binance for BTCUSDT and ETHUSDT): Task 1's fetcher calls `fetchKlines('https://api.binance.com', symbol, ...)` for both symbols (symbol is a `workflow_dispatch` choice, defaulting to BTCUSDT, with ETHUSDT supported).
- **DATA-05** (read `X-MBX-USED-WEIGHT-1M`, honor `Retry-After` on 429, back off on 418): Task 1's `decideBackoff` + the fetcher's retry loop, unit-tested. `fetchKlines` already captures the weight header (Phase 1) and classifies 429/418 as `BinanceError` with `retryAfter`.
- **SC1** (fetch half): Task 1/2 fetch a batch of up to 1000 candles per run and deliver them to the ingest endpoint (which stores them — plan 02-01). Together they make SC1 true end-to-end.
- **SC2** (driver half): each run advances the stored cursor by one batch; Task 2's verify runs the fetcher twice and confirms the cursor moves forward (02-01's endpoint owns the cursor storage; this plan drives it). The Worker-side ingest stays within Free CPU/subrequest limits (verified in 02-01).
- **SC3** (429/418 → back off or honor Retry-After instead of erroring out or hammering the API): Task 1's backoff logic + tests; the fetcher sleeps per `Retry-After` before a single retry on 429 and aborts (no auto-retry) on 418.

## Dependency Graph

- Task 1 (backoff module + fetcher script + unit tests) → Task 2 (workflow rewrite + secrets + end-to-end verify). Builds on plan 02-01's deployed ingest/cursor endpoints and Phase 1's `src/lib/binance.ts`. No other phase-2 plan depends on this one; Phase 3 (Historical Load & Cron Sync) will reuse the same fetcher for the scheduled daily cron.

    - `export function decideBackoff(err: BinanceError): BackoffDecision`
      - status 429 → `{ action: 'retry', waitSeconds: parseRetryAfter(err.retryAfter) ?? 60, message: 'rate limited, honor Retry-After' }` (hardcoded 60s is only the floor when the header is missing — never the only strategy, per PITFALLS.md).
      - status 418 → `{ action: 'abort', waitSeconds: parseRetryAfter(err.retryAfter) ?? 120, message: 'IP auto-banned, must back off; do NOT auto-retry (retrying extends the ban)' }`.
      - any other status → `{ action: 'abort', waitSeconds: null, message: 'non-retryable HTTP status' }`.
    - `export function sleep(ms: number): Promise<void>` — `new Promise(r => setTimeout(r, ms))`.
