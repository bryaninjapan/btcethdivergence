🎯 Top Recommendation

Start with: Candidate #1 — Timestamp Conversion Leakage

This is the highest-leverage intervention. Why:

  • Affects 8+ backend modules — timestamp conversions repeat across routes, services, lib
  • Seam problem — milliseconds ↔ seconds boundary is leaking; should be enforced in one layer

Candidate #1: Timestamp Conversion Leakage (Seam Problem)

Strong

Consolidate scattered timestamp conversions into a single temporal-api policy layer.

Files & Modules Involved

  • • src/lib/timestamp.ts (core wrapper)
  • • src/lib/db.ts:52 (listRecords)
  • • src/lib/binance.ts:18 (fetch)
  • • src/routes/klines.ts:30-31
  • • src/services/admin.service.ts:129
  • • src/lib/kline-insert.ts (backfill)
  • • public/js/timestamp.js (frontend mirror)

Key Friction Points

  • Seam leak: Milliseconds ↔ seconds conversions scattered across 8+ modules
  • Repeated calls: Every consumer calls .toSeconds(), .toMillis(), .fromMillis()
  • Frontend duplication: Timestamp.js copied from backend, no synchronization
  • Locality problem: Understanding temporal boundaries requires reading multiple files

Current Architecture (Shallow Interface)

Routes accept milliseconds (browser Date.now()), services and database work in seconds. Conversion logic is scattered: Timestamp.fromMillis(ms).toSeconds() appears in klines.ts, admin.service.ts, and kline-insert.ts independently. Frontend has its own Timestamp implementation, requiring parallel maintenance. Each conversion site is a seam where temporal semantics could be violated.

Proposed Solution (Deepen Module)

Create src/lib/temporal-api.ts — a single policy layer enforcing temporal boundaries:

// src/lib/temporal-api.ts

export const TemporalAPI = {

// Routes enter here (browser milliseconds)

fromBrowserTime(ms: number): number {

return Math.floor(ms / 1000)

},

// Convert to browser time for API response

toBrowserTime(sec: number): number {

return sec * 1000

},

// Internal DB queries use seconds (implicit contract)

}

Routes call TemporalAPI.fromBrowserTime(startMs) once at entry. Services and db.ts work exclusively in seconds (number type, no wrapper). Remove Timestamp type from internal modules — use semantically commented numbers instead. Move Timestamp to a boundary adapter used only at HTTP entry/exit.

Benefits

  • Centralized seam enforcement: Temporal boundary has one policy, not 8+ scattered conversions.
  • Improved locality: Understanding "how time flows" requires reading one module, not tracing through routes + services + db.
  • Reduced leverage friction: Adding timezone support or date-range queries no longer requires cascading changes.
  • Frontend coherence: Share divergence types and temporal constants via API schema, not hardcoded .js files.
  • Testing explosion: Temporal-api tests verify conversions happen exactly once per request path.

Candidate #2: Divergence Domain Duplication (Poor Locality)

Strong

Unify divergence type definitions across backend and frontend; single source of truth.

Files & Modules Involved

  • • Backend: src/domains/divergence.ts (lines 3–14)
  • • Frontend: public/js/divergence.js (lines 3–21) [identical copy]
  • • src/lib/validate.ts (imports from domains)
  • • public/js/records.js (imports from divergence.js)
  • • public/js/charts.js (uses type labels)

Key Friction Points

  • 1:1 duplication: DIVERGENCE_TYPES, TYPE_LABELS, MSB_LABELS copied exactly
  • No shared contract: Frontend imports ./divergence.js; backend imports ../domains/divergence
  • Seam leak: Business knowledge (domain model) bleeds across API without schema
  • Maintenance burden: Adding a type requires syncing 2 files

Current Architecture (Scattered Concept)

Backend defines DIVERGENCE_TYPES in src/domains/divergence.ts. Frontend has an identical copy in public/js/divergence.js. When a new divergence type is added, changes must propagate to both files. There is no API schema contract ensuring synchronization.

Proposed Solution (Deepen Locality)

Option A (API-First): Fetch type metadata from backend:

// GET /api/schema/divergence-types

{ types: ["btc_hh_eth_lh", "btc_lh_eth_hh", ...], labels: {...}, msb: ... }

// Frontend bootstraps from API response, not hardcoded .js

Option B (Build-Time Generation): Generate public/js/divergence.js from backend src/domains/divergence.ts during build.

Benefits

  • Single source of truth: Types defined once, consumed everywhere.
  • Improved locality: Understanding divergence types requires reading one module.
  • Reduced leverage friction: Adding a type is a one-file change.
  • Type-safe API contract: Validation schemas on backend match frontend UI.
  • Testable schema: E2E test: frontend loads types from API, UI renders them correctly.

Candidate #3: Chart State Fragmentation (Scattered Concerns)

Worth Exploring

Merge chart-state, chart-range, and chart-sync into a unified state machine module.

Files & Modules Involved

  • • public/js/chart-state.js (factory, 83 lines)
  • • public/js/chart-range.js (time window logic)
  • • public/js/chart-sync.js (subscription handler)
  • • public/js/charts.js (orchestrator, lines 14–18, 73–140)

Key Friction Points

  • Scattered state concern: Understanding "chart state" requires reading 4 files
  • Shallow interface: Factory wraps properties, not logic; boilerplate adds little value
  • No state machine: Mutations scattered; no explicit state transitions
  • Poor locality: Modifying "synced zoom" requires touching 3 files

Current Architecture (Shallow State)

Chart state is split across three modules: factory pattern in chart-state.js, time calculations in chart-range.js, and subscription handling in chart-sync.js. Understanding the full lifecycle requires bouncing between them. The interface is just wrappers around object properties — minimal business logic.

Proposed Solution (Deepen with State Machine)

Merge into single public/js/chart-manager.ts (TypeScript) with explicit state machine:

type ChartState = "LOADING" | "LOADED" | "SYNCED_TO_RANGE" | "ERROR"

export class ChartManager {

load(symbol: string, range: Range) → "LOADING"

onDataReady() → "LOADED"

syncToRange(otherChart: ChartManager) → "SYNCED_TO_RANGE"

}

Benefits

  • Improved locality: All chart-related logic in one module; understand state lifecycle in one file.
  • Reduced leverage friction: Modifying sync behavior means editing one module, not three.
  • State machine clarity: Explicit transitions (LOADING → LOADED → SYNCED) prevent invalid states.
  • Testing explosion: Unit tests for state transitions; mock Lightweight Charts subscriptions once.

Candidate #4: Shallow Records Service Wrapper (Minimal Leverage)

Worth Exploring

Raise service interface from thin wrapper to rich query repository with business logic.

Files & Modules Involved

  • • src/lib/db.ts:9–31 (listRecords, createRecord, etc.)
  • • src/services/records.service.ts:64–73 (wrapper)
  • • src/routes/records.ts:16–28 (HTTP handler)
  • • src/lib/test-db.ts (test fixtures)

Key Friction Points

  • Shallow interface: Service adds only try/catch → DatabaseError
  • No business logic: Each CRUD is 2–10 lines: bind, execute, return
  • Scattered validation: Zod validates before service is called; little value added
  • Test duplication: Must mock both db.ts and records.service.ts separately

Current Architecture (Thin Wrapper)

records.service.ts wraps db.ts functions: route calls service, service calls db, returns result or throws DatabaseError. No validation (already done in Zod). No caching. No filtering logic. The interface complexity ≈ implementation complexity — textbook shallow module.

Proposed Solution (Raise Interface)

Elevate service from thin wrapper → rich query repository with business semantics:

export class RecordsRepository {

listWithStats(filters) →

{ records: [], totalCount, tagCloud, typeDistribution }

findByTimeRange(startTime, endTime) → []

upsertWithMerge(id, payload) → merged record

}

Move error handling to middleware (centralized, reusable). Consolidate SQL building into QueryBuilder subclass per entity.

Benefits

  • Reduced test count: No need to mock db.ts + service separately; test routes directly.
  • Richer interface: Repository methods express business intent (listWithStats, upsertWithMerge).
  • Improved locality: Related queries grouped; schema changes handled in one place.
  • Leverage: Adding new filter (e.g., "by creator") requires one repository method, not multi-file changes.

Candidate #5: Calculator Validation Duplication (Future Debt)

Speculative

Extract calculator rules to backend; prepare for API endpoint without duplication.

Files & Modules Involved

  • • public/js/calculator-init.js:71–87 (manual validation, Chinese strings)
  • • src/lib/validate.ts (has schemas for records, not calculator)
  • • No backend calculator endpoint yet

Key Friction Points

  • Client-only logic: Validation hardcoded in calculator-init.js, not shared
  • Error strings in Chinese: Not i18n-ready; localizable error codes missing
  • Future duplication risk: If /api/calculator added, rules will duplicate again

Current Architecture (Speculative Debt)

Calculator validation is entirely client-side, hardcoded in Chinese. If an API endpoint is added later, validation rules will be rewritten for the backend, causing drift.

Proposed Solution (Prepare for Growth)

Extract rules to src/domains/calculator.ts (Zod schema + types). Frontend keeps independent client-side validation (fast feedback). When /api/calculator is added, reuse the backend schema.

Benefits

  • Future-proof: Adding API endpoint won't cause duplication.
  • Auditability: Validation rules documented in one module, easier to audit for correctness.
  • i18n-ready: Error codes instead of hardcoded strings.

Note: This candidate is speculative — only address if a calculator API is planned. Low priority for v1.0.
